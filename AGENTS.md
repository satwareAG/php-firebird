# AGENTS.md

## About php-firebird

**php-firebird** is a modernized PHP extension providing native connectivity to Firebird databases (3.0, 4.0, 5.0+). It is a high-performance replacement for the legacy `ext/interbase`, written in C/C++17 using the modern Firebird OO API.

The project follows **Spec-Driven Development (SDD)** and targets high-quality API standards for modern PHP (8.2+).

---

## API Architecture

The extension provides three distinct layers:

| Layer | Type | Namespace / Prefix | Purpose |
|-------|------|-------------------|---------|
| **Layer 1** | Procedural | `fbird_*` | Low-level, high-performance C API functions |
| **Layer 2** | OOP | `Firebird\*` | Native PHP classes (`Connection`, `Transaction`, etc.) |
| **Layer 3** | PDO | `pdo_fbird` | Separate extension providing `fbird:` DSN prefix |

### Branch hygiene: main is squash-merge-only

Content lands on `main` as single squash commits, so commit-graph ancestry does
NOT prove a branch's content is merged. Before deleting a branch, verify via the
merged-PR record (`gh pr list --head <branch> --state merged`) or a content grep
against `main`; PR-review checkouts (`pr-*`) are disposable duplicates of already
merged branches. Tags, not branches, are the immutable release record.

## Branch Provenance (#688-P5)

Every work branch MUST be cut from the freshly fetched origin/main tip - a branch cut from a stale local main shipped the wrong .gitignore in the 2026-10-29 near-miss (caught by accident; now enforced).

- Gate: `bash scripts/branch-provenance.sh main` - exit 0 = the branch contains origin/main's tip; exit 1 = stale base (merge main into the branch or re-cut from the fetched tip).
- Run at session start per branch and before opening a PR; optionally wire as a pre-push hook (refuses pushing a branch that lacks origin/main's tip).
- The script distinguishes stale base (FAIL) from fast-forward-available (WARN - pull main, re-verify).

## Test Running

### Docker-first local development (primary)

All local development - build, test, and ad-hoc debugging - runs inside the
Docker containers. Host builds are NOT supported for dev/test work
(`.so` files built on the host fail to load in containers; see parity rule 3
below).

Canonical flows:

```bash
# Single container, build + specific test (preferred for RED/GREEN loops)
bash scripts/test_matrix.sh php84-fb3-dev "" tests/<test>.phpt

# Full 12-container matrix (PHP 8.2-8.5 x FB3/FB4/FB5)
bash scripts/test_matrix.sh

# Ad-hoc PHP script inside a running container MUST replicate the runner's
# env contract (FIREBIRD_HOST + FIREBIRD_DB_DIR), not just the extension flag:
docker compose -f docker/docker-compose.yml exec \
  -e FIREBIRD_HOST=firebird30 -e FIREBIRD_DB_DIR=/tmp php84-fb3-dev \
  php -n -d extension=/ext/modules/firebird.so /ext/diag.php
```

Without the env contract, an ad-hoc script hits a different database topology
and fails with misleading errors ("Table unknown RDB$TABLES" on a fresh DB,
phantom lock conflicts) even though identical code passes under the canonical
runner (lesson 2026-09-16, #624 session).

### `make test` only loads the main extension

`make test` uses the Makefile generated by `phpize`, which only loads `firebird.so`.
The `PHP_TEST_SHARED_EXTENSIONS` env var is NOT read by the extension Makefile's `test`
target. As a result, `pdo_fbird.so` is never loaded, and all PDO tests SKIP silently.

**Correct way to run tests** (used by CI):
```bash
php run-tests.php \
  -d extension=modules/firebird.so \
  -d extension=pdo_fbird/modules/pdo_fbird.so \
  -p $(which php) \
  tests/
```

### pcntl double-loading

PHP Docker containers (`php:*-cli`) load `pcntl` via `docker-php-ext-install` (php.ini).
Adding `-d extension=pcntl.so` when already loaded causes "Module already loaded" warning
in every test's output, failing all tests. Fix: check `extension_loaded('pcntl')` first.

### Debug/ASAN builds enforce handwritten arginfo (release builds do not)

Debug PHP builds (the `php83-asan` container) fatal with
`Arginfo / zpp mismatch` / `Return value must be of type ...` when the runtime
violates the handwritten `arginfo_*` macros in `firebird.c` - release
builds tolerate the same violations silently. Consequence: a green release
suite says NOTHING about arginfo conformance; before 3c051d5 every test
BORKed at SKIPIF under php83-asan because `init_db()` (tests/firebird.inc)
creates its DB through `fbird_query(FBIRD_CREATE, ...)`.

Rules:
- After changing any `ZEND_BEGIN_ARG_*` block or a function's
  `zend_parse_parameters` format, run at least one touched test under
  `php83-asan` (`docker compose up -d php83-asan && docker compose exec
  php83-asan /ext/scripts/test.sh <test>`).
- Cross-container builds fight over `modules/` ownership (asan runs as
  root, others as uid 1000): `docker compose exec -u root <svc> chown -R
  1000:1000 /ext` before building in another container.
- Known open arginfo/lifecycle latents visible only under asan: #593-596.

### CRITICAL: Local/CI Environment Parity

**Never assume "passes locally" means "passes in CI".** The two environments must
be kept in sync. Three hard-won lessons:

1. **Firebird client version MUST match**: Local Docker containers must use the
   same Firebird client as CI (official tarball from GitHub releases, NOT Debian
   apt `firebird-dev`). The apt package installs FB3 client headers, which compiles
   out all `#if FB_API_VER >= 40` code (DECFLOAT, INT128, timezones). Tests silently
   skip instead of exercising the code. See: `scripts/verify-ci-parity.sh`.

2. **`FIREBIRD_DB_DIR` MUST be set in CI**: The procedural path (`firebird.inc`)
   uses `FIREBIRD_DB_DIR` to create a unique database per test. The PDO path
   (`pdo_fbird.inc`) uses `FIREBIRD_DB_PATH` for the shared database. If only
   `FIREBIRD_DB_PATH` is set, both paths use the same database, causing metadata
   lock conflicts when tests do `RECREATE TABLE` from different connections.

3. **Build INSIDE the target container**: `.so` files compiled on a host with a
   different glibc version will fail to load in Docker containers. Always run
   `scripts/build.sh` inside the container, never on the host.

### Test timeout

Both CI and local `run-tests.php` use `--set-timeout 15` to kill hanging tests
in 15 seconds instead of the default 60. This prevents a single hanging test from
cascading into a 30-minute CI timeout.

### zpp default/forwarding changes require wire-observation tests in the same PR (#681)

The #671 class: a zpp-parsed argument (`sync`) silently DISCARDED, plus a
hardcoded literal (`0`) reaching the attach DPB. Signature and return-value
tests cannot see either; v13.0.0 shipped it and 11 release trains kept it.

- Any PR changing `zend_parse_parameters` defaults, argument forwarding, or
  DPB/SPB/TPB buffer building MUST include a test observing the wire/engine
  effect (MON$ column, header state via the service API, service output),
  not only return values.
- Enforcement: `scripts/gates/issue-681-zpp-wire-gate.sh` (CI job
  `zpp-wire-gate` in code-quality.yml + locally; fails the diff when the zpp
  surface changes without a `.phpt` change; `--selftest` doubles as the
  negative control). Detection layers: diff-line tokens (zpp/arginfo/DPB-
  SPB-TPB items), the forwarding locus itself (`largs[]`/`args[SYNC]`/
  `params.(force_write|dialect|...)` - the literal #671 line carries no DPB
  token), and connect-path files (fbird_connection.c, firebird_utils.cpp -
  the fbc_connect* params-assembly locus, PDO driver, src/cpp/fb_*.hpp)
  which are wire-surface by definition. Fail-closed: a diff error fails the
  gate; the token check diffs the requested range (PR mode), not HEAD.
- Review checklist: for every parsed argument, confirm it is FORWARDED to the
  implementation (grep the call chain). Parsed-but-unforwarded = dead
  parameter, blocks merge (#595/#671 family).
- Independent (non-author) review required for connect-path argument changes.
### Shell gates: no `grep -q` under pipefail, no `head` in extraction pipelines (#676)

`cmd | grep -q 'pattern'` under `set -o pipefail` is a false-negative generator:
`grep -q` exits at the first match, the producer dies of SIGPIPE (exit 141) if it
writes more data afterwards, and `if !` reads 141 as no-match. Symptom observed:
intermittent "firebird extension not loaded" / "container not running" on healthy
hosts. Rule: in any pipeline whose producer may outlive the match, use non-quiet
grep redirected to /dev/null (`grep -i 'x' >/dev/null`) - it reads to EOF. File
greps keep `-q` (no pipe producer, no hazard).

Same class for report pipelines: end extractions in consuming limiters
(`sed -n '1,80p'`), never `head` - a head-closed pipe SIGPIPEs the upstream and,
with the ERR trap, aborts the whole report mid-flight (only manifests on outputs
larger than the 64KB pipe buffer). Regression oracle: `scripts/gates/issue-676-oracle.sh`
(three stub variants; v3 grows the log past the buffer size so the hazard is
observable). Meta-rule the oracle taught us: attribute every RED before trusting
it - the first negative-control run failed for an unrelated cause and masked the
real defect behind it.

### The 12-lane matrix shares one tree: no branch switches mid-run

All matrix lanes bind-mount the same working tree (`..:/ext`). A `git checkout`
while `scripts/test_matrix.sh` runs swaps the tree under live lanes: tests vanish
mid-run (`Cannot open test file`) and later lanes silently test the wrong code
(happened 2026-10-29 during v13.2.12 verification). Sequence: run the matrix to
completion, THEN switch branches. Additionally, lanes accumulate build state in
the shared tree - when a lane fails oddly (e.g. a segfault that origin/main does
not reproduce), re-run that lane in isolation with a clean rebuild before
diagnosing code: a stale in-container `.so` from a previous lane's build can
produce wrong-cause failures (seen on php85-fb3-dev, 2026-10-29).

### Issue filing: environment specs are mandatory (#673)

Bug reports use `.github/ISSUE_TEMPLATE/bug_report.yml`; the five environment
fields are required: extension version, PHP version/build/SAPI, client OS+arch,
Firebird server version, connect API (procedural/OOP/PDO). Agents filing issues
fill them. Note for template edits: GitHub dropdown options must be plain YAML
strings - an unquoted scalar containing `: ` parses as a mapping and GitHub
rejects the whole form; `scripts/gates/issue-673-oracle.py --selftest` is the
negative control.

### IStatus lifecycle: prefer RAII, "let it leak" is safe

**Verification note**: Cross-referenced with Firebird source - `JProvider::attachServiceManager`
(`src/jrd/jrd.cpp:4327`) uses `ThreadContextHolder` locally; `Dispatcher::attachServiceManager`
(`src/yvalve/why.cpp:6645`) passes a fresh `FbLocalStatus` to the underlying provider. The
caller's IStatus is **never** persisted by `attachServiceManager()`.

**`Firebird::CheckStatusWrapper` is non-owning**: Per `Interface.h:165-330`, its destructor is
implicit and does NOT call `dispose()`. Code using
`Firebird::CheckStatusWrapper status(master->getStatus());` directly is **leaking** the
IStatus (~80 bytes/call), not disposing it. Use `fb::CheckStatusScope` (RAII) for proper
lifecycle management.

**Default rule**: Use `fb::CheckStatusScope` for new code. Existing "let it leak" patterns
are safe but accumulate leaks - acceptable for short-lived CLI, problematic for long-lived
PHP-FPM workers. When in doubt, let the IStatus leak rather than risk a crash.

**Service attach in tests**: Use `getenv('FIREBIRD_HOST') ?: 'localhost'` instead of hardcoded
`"localhost"`. The Firebird client library's local protocol (Unix socket, triggered by
`"localhost"`) can SIGSEGV on connection failure in CI environments. TCP protocol (triggered
by hostname) fails gracefully. See `tests/client_coverage/fb3_wire_protocol.phpt` for the
correct pattern.

## Release Procedure

### Pre-Tag Checklist

1. **Verify CI green**: `bash scripts/verify-ci-green.sh` - the 4 gated workflows must pass (ci, code-quality, sanitizers, coverage). doctrine-downstream is dispatched automatically when gating paths (C/C++, pdo_fbird, stubs) changed since the last release tag and waited out to green; otherwise the run is skipped (PR/weekly coverage stands). Rejects runs whose head SHA does not match the local branch head. Auto-retries queue-starvation false-reds once (ALL failing jobs cancelled with zero executed steps, #663); waits up to `CI_GREEN_RERUN_TIMEOUT` s (default 1500) per starved workflow, so worst case adds ~25 min per affected workflow.
2. **Verify CI parity**: `bash scripts/verify-ci-parity.sh` - local Docker client must match CI
3. **Run local test matrix**: `bash scripts/test_matrix.sh` - all 12 containers must pass (PHP 8.2-8.5 x FB 3.0/4.0/5.0)
   - **3.5 Run tag-gate delta (#680)**: `bash scripts/test-delta.sh <previous-release-tag> "tests/issue671* tests/issue682*" php84-fb3-dev` - build the previous release tag in a disposable worktree, run the CURRENT wire-behavior oracle suite against it, and ADJUDICATE every behavior delta with a `scripts/delta-allowlist.txt` entry (reason + CHANGELOG/UPGRADING reference). Unadjudicated deltas fail the gate; the negative control is `bash scripts/gates/issue-680-delta-negative-control.sh` (seeds the #671 regression into the previous tag and requires the delta run to catch it).
4. **Run amicron-platform downstream**: `AMICRON_PLATFORM_DIR=<local private checkout> DBPASS=masterkey bash scripts/test-amicron-platform.sh` - verify customer stack (checkout paths are environment-specific; this public repo never records internal filesystem paths)
5. **Verify version stamps**: `bash scripts/check-version-stamps.sh`
6. **Update CHANGELOG.md** with release notes
7. **Bump version**: Update `VERSION.txt` and `stubs/*.php` `@version` tags

### Tagging Rules

- **NEVER force-push a tag.** Once `git push origin v*` succeeds, the tag is immutable.
- If a release is broken: delete tag + release entirely, fix, re-tag with a NEW tag (e.g., `v12.1.1`).
- Tag format: `vMAJOR.MINOR.PATCH` (e.g., `v12.1.0`)

### Release Pipeline Architecture

```
Tag push v*
  |
  +-- CI, Code Quality, Sanitizers, Coverage (validation, already passed)
  |
  +-- Release (Linux)   -> prepare -> build -> test-bundles -> upload (draft:true)
  +-- Release (macOS)   -> prepare -> build -> test-bundles -> upload (draft:true)
  +-- Release (Windows) -> get-matrix -> build -> upload (draft:true)
  |
  +-- Split Packages     -> split stubs/ to satwareAG/php-firebird-stubs
  |                      -> split pdo_fbird/ to satwareAG/pdo-fbird (PIE)
  |
  +-- Publish Release   -> waits for all 3 platform workflows
                           -> generates SLSA attestations
                           -> generates checksums
                           -> publishes release (draft:false)
```

**Key rules**:
- Platform workflows upload with `draft: true` via `softprops/action-gh-release@v3`
- The `publish-release.yml` workflow is the ONLY one that flips `draft: false`
- SLSA attestations are generated centrally in `publish-release.yml`
- The split-stubs workflow deletes any pre-existing tag in the stubs repo before re-creating

# DOX framework

- DOX is highly performant AGENTS.md hierarchy installed here
- Agent must follow DOX instructions across any edits

## Core Contract

- AGENTS.md files are binding work contracts for their subtrees
- Work products, source materials, instructions, records, assets, and durable docs must stay understandable from the nearest applicable AGENTS.md plus every parent AGENTS.md above it

## Read Before Editing

1. Read the root AGENTS.md
2. Identify every file or folder you expect to touch
3. Walk from the repository root to each target path
4. Read every AGENTS.md found along each route
5. If a parent AGENTS.md lists a child AGENTS.md whose scope contains the path, read that child and continue from there
6. Use the nearest AGENTS.md as the local contract and parent docs for repo-wide rules
7. If docs conflict, the closer doc controls local work details, but no child doc may weaken DOX

Do not rely on memory. Re-read the applicable DOX chain in the current session before editing.

## Update After Editing

Every meaningful change requires a DOX pass before the task is done.

Update the closest owning AGENTS.md when a change affects:

- purpose, scope, ownership, or responsibilities
- durable structure, contracts, workflows, or operating rules
- required inputs, outputs, permissions, constraints, side effects, or artifacts
- user preferences about behavior, communication, process, organization, or quality
- AGENTS.md creation, deletion, move, rename, or index contents

Update parent docs when parent-level structure, ownership, workflow, or child index changes. Update child docs when parent changes alter local rules. Remove stale or contradictory text immediately. Small edits that do not change behavior or contracts may leave docs unchanged, but the DOX pass still must happen.

## Hierarchy

- Root AGENTS.md is the DOX rail: project-wide instructions, global preferences, durable workflow rules, and the top-level Child DOX Index
- Child AGENTS.md files own domain-specific instructions and their own Child DOX Index
- Each parent explains what its direct children cover and what stays owned by the parent
- The closer a doc is to the work, the more specific and practical it must be

## Child Doc Shape

- Create a child AGENTS.md when a folder becomes a durable boundary with its own purpose, rules, responsibilities, workflow, materials, or quality standards
- Work Guidance must reflect the current standards of the project or user instructions; if there are no specific standards or instructions yet, leave it empty
- Verification must reflect an existing check; if no verification framework exists yet, leave it empty and update it when one exists

Default section order:
- Purpose
- Ownership
- Local Contracts
- Work Guidance
- Verification
- Child DOX Index

## Style

- Keep docs concise, current, and operational
- Document stable contracts, not diary entries
- Put broad rules in parent docs and concrete details in child docs
- Prefer direct bullets with explicit names
- Do not duplicate rules across many files unless each scope needs a local version
- Delete stale notes instead of explaining history
- Trim obvious statements, repeated rules, misplaced detail, and warnings for risks that no longer exist

## Closeout

1. Re-check changed paths against the DOX chain
2. Update nearest owning docs and any affected parents or children
3. Refresh every affected Child DOX Index
4. Remove stale or contradictory text
5. Run existing verification when relevant
6. Report any docs intentionally left unchanged and why

When the user requests a durable behavior change, record it here or in the relevant child AGENTS.md

## Honesty

Claims in all agent output (docs, posts, replies, reports) must be evidence-backed and bounded by what the evidence supports:

| Rule | Detail |
|------|--------|
| No cross-domain comparisons | Never compare against a different class (datacenter vs home rig, home model vs frontier model) unless the comparison is backed by data. State "different problem" instead |
| Caveat in the same sentence | The limitation belongs next to the claim, not dropped or footnoted: "5.8 tok/s - slow, but zero marginal cost", never "fast, zero marginal cost" |
| Resolve conflicts before publishing | When numbers conflict across sources (transcript vs description vs post), resolve before publishing. Never ship both values |
| Concede in technical contexts | Admitting the limitation is what makes technical content read as genuine; promotion without concession reads as astroturf |
| Unverified is stated as unverified | A claim that cannot be checked against a primary source is labeled unverified or omitted |
| Artifact honesty | A shipped artifact that reports identity/version (stamps, `phpversion()`-style APIs) MUST tell the truth; placeholder or borrowed values are rejected at a release gate. Applies when the project ships versioned binaries |
| Generated drift | Repeated facts (versions, counts, inventories) derive from one named authority, generated not hand-copied; CI regen-diff enforces it - point at the generator or fixture, never duplicate the values |
