# 2026-03-04: v7.2.0 Release CI/CD Debugging

## Summary

After releasing php-firebird v7.2.0 (PHP 8.2+ minimum, Firebird 3.0+ minimum,
ibase_* removed), three downstream compatibility MRs/PRs were opened. CI
debugging revealed two root causes in the amicron-platform MR.

---

## Problem 1: Composer `-q` flag hides resolution errors

### Error

`composer -q --dev install` exits 1 with no output — impossible to diagnose.

### Fix

Temporarily remove `-q` to expose the full error:

```bash
sed -i 's/composer -q --dev install/composer --dev install/' .gitlab-ci.yml
```

### Lesson

Never use `-q` on `composer install` in CI without a fallback error handler.
Use `composer install 2>&1 | tee composer-output.log` or remove `-q` entirely.

---

## Problem 2: CI Docker image PHP version mismatch

### Error

```text
Problem 1
  - Root composer.json requires php ^8.2 but your php version (8.1.34) does not satisfy that requirement.
```

### Root Cause

`image: webdevops/php-apache-dev:8.1` — the CI image was PHP 8.1 but
`composer.json` was updated to require `php: ^8.2`.

### Fix

```yaml
# .gitlab-ci.yml
image: webdevops/php-apache-dev:8.2  # was 8.1
```

### Lesson

When bumping minimum PHP version in `composer.json`, **always update the CI
Docker image tag simultaneously** in the same commit. Add a checklist item to
the PHP version bump PR template.

## Problem 3: Transitive dependency version pin conflict

### Error

```text
Problem 2
  - satag/amicron-entity-bundle 5.3.0 requires satag/doctrine-firebird-driver 3.0.2
    -> conflicts with your root composer.json require (3.0.x-dev).
```

### Root Cause

`satag/amicron-entity-bundle 5.3.0` pins `satag/doctrine-firebird-driver`
to exactly `3.0.2`. Our MR had bumped the constraint to `3.0.x-dev` (dev
branch alias), which Composer cannot satisfy alongside the exact pin.

### Fix

Revert `satag/doctrine-firebird-driver` to `^3.0` (resolves to 3.0.2):

```json
"satag/doctrine-firebird-driver": "^3.0"
```

The `ext-firebird: ^7.2.0` platform override in `composer.json` is sufficient
to enforce the new extension version requirement.

### Lesson

When a transitive dependency has an exact version pin, do not use dev branch
aliases (`x.y.x-dev`) in the root `composer.json`. Use the semver constraint
(`^x.y`) that resolves to the pinned version.

## Problem 4: Cache key not invalidated after image change

### Error

Even after fixing `composer.json`, the old `vendor/` cache (built with PHP 8.1
and old dependencies) was restored, causing the same failure.

### Fix

Bump the cache key suffix in `.gitlab-ci.yml`:

```yaml
cache:
  key: "$CI_COMMIT_REF_SLUG-2"  # was "$CI_COMMIT_REF_SLUG"
```

### Lesson

When changing the PHP image version or major dependency constraints, always
bump the cache key to force a fresh `vendor/` install. Convention:
`$CI_COMMIT_REF_SLUG-{N}` where N increments on breaking cache changes.

## GitLab API: Cache clearing requires runner_id

The GitLab API endpoint `DELETE /projects/:id/runners/caches` requires
`runner_id` — it cannot clear all caches for a branch without it. The
workaround is to bump the cache key in `.gitlab-ci.yml`.
